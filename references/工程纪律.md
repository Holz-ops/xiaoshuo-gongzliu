# 工程纪律（目录 / 文件 / 版本 / 成果物 / 脚本）

从 SKILL.md 本体搬出的操作细则。SKILL.md 只留三行硬规矩，细节在此按需读。

---

## 目录分层（编号＝流程层号）

项目目录按流程分层编号，**哪一层出问题就回哪个文件夹找**：

```
00 skill的内容\     流程说明 + 流程图（skill 本体留在书外，别复制进来）
001 世界观\         设定资料（人物 / 时间线 / 体系…按书需要）· 设定基准表 · 校验词典
     报告\               ① 报告的落点（题材 · 基调 · 资料）
003 梗概\           梗概
004 目录\           章节表 · 先行章纲（写前定，**冻结**）
005 章纲\           总结章纲（**后续以此为准**）· 章纲回填 · 编号对照表
006 文章\           ← 稿子的三个位置 + 错题本（见下）
     扩展文章\           ① 初稿
     ai复查文章\         ② AI 排查改完的
     人工复查文章\       ③ 人工排查改完的
     错题本\             改稿时就近看（工作副本；主本在 009 其他\问题本\）
007 最终文章\       ← ④ 定稿（交付用）
008 进度\           上下文压缩包 · 续写档案 · 进度卡 · 未解决清单 · 文件地图
009 其他\           ← 三样支援（不在步骤里，少了会丢东西）
     版本\               快照 · _原稿(只读) · 版本索引 · 改动说明 ← **数据不流失**
     问题本\             ai查出的\ · 人查出的\ ← **教训不丢**
     批次成品\           每批一包（见下）← 给人读的唯一入口
     归档\               废弃流程与旧文档
```

**编号 + 中文名，层级尽量浅。** 编号由项目主人定（`002` 目前留空）。

由 `scripts/init_book.py` 一次建好；目标目录已有内容时拒绝执行，防止把新流程塞进已有的书里。

## 文章怎么走（两轮排查，每轮都留「意见 + 文章」）

```
① 写出来     → 006 文章\扩展文章\          第一层：按章纲扩写
② AI 排查    → 006 文章\ai复查文章\        查出的问题进 009 其他\问题本\ai查出的\
③ 人工排查   → 006 文章\人工复查文章\      人提的意见进 009 其他\问题本\人查出的\
④ 定稿       → 007 最终文章\               通过，交付用
```

**文章走哪一格、问题就记在哪一本问题里**——哪个环节有问题就在那一环里找。

### 铁律：没过人的那一关，绝不放「最终文章」

| 文章的状态 | 该在哪一格 |
|---|---|
| 刚扩写完，还没查 | `006 文章\扩展文章\` |
| AI 检查/改完了，**等人确定** | `006 文章\ai复查文章\` |
| 人确定/改完了，通过 | `006 文章\人工复查文章\` |
| 通过复查、**真正定稿** | `007 最终文章\` |

把"待定"的稿子放进「最终文章」，等于**把还没验收的东西当成品交付**，流程就白跑了。放之前先问一句：**人的那一关过了吗？**

**每搬一步，旧版先存进 `009 其他\版本\`——所以任何一版都能翻回来对比，数据不流失。**

改稿（已有成稿要修订）也走同一条路：从 `007 最终文章\` 取出 → 走 ②③ → 回 `007 最终文章\`。

### 当前稿唯一，历史版本可多份（v1.2.5 起明确）

> 此前"只一个位置"与"改前留扩展文章"两条规则互相打架，导致同一章"有时有有时没有"。

- **当前稿**（同一章同时只能有一个）：`ai复查文章` / `人工复查文章` / `最终文章` **三选一**
- **`扩展文章` 是初稿归档（只读）**：⑥ 之后允许保留，用于对照与回滚；它**不算当前稿**，不违反"唯一"
- **`009 其他\版本\`** 存每次改动前的快照，**可多份**；旧稿进了版本库，就不要再占当前格
- **每批完成后跑一次** `python scripts/article_index.py <书目录>`：缺章、多处当前稿、空文件会直接列出来；加 `--write` 生成 `008 进度\文章索引.md`

md 源与 docx 交付版保持同一套分层，两边一一对应。

## 改稿纪律：改前先快照

正文是**原地覆盖**的。动笔之前，先把这批要改的 md 复制到 `009 其他\版本\快照\<日期>-<批次>前\`，再开改；要留 docx 对照就再存一份到同目录；改完在进度卡里记一句快照路径。

> 不留快照的后果是真实的：改完就永远拿不回"改前版本"，事后再想做改前/改后对照已经不可能。
> 快照放在版本目录里不会干扰脚本——`count_chars.py`、`check_consistency.py`、`md2docx.py` 都只扫一级 `*.md`。
> **不需要"批后快照"**——下一批的"批前"自然包含这一批的"改后"。
> 同理，`_原稿`、`_说明` 这类结构文件一律用下划线开头，与正式交付文件区分开。

**同一条规则也管"清洗"**：清盗版水印、统一编码、去重复段这类操作同样不可逆，动之前也要先快照，且**产物另存一份，不要在源目录上就地改**（源目录只读）。实测教训：一段正则清完水印，如果同时吃掉了正文（水印块的正则常带 `[^\n]{0,90}`，会把紧跟其后的句子一起卷走），没有快照就再也分不清"原文本该是什么"。

## 字数：两个口径，各管一段

- 平台规格：**每章 2000~3000 字**
- 共同点：都是**去空白后的字符数（含标点）**
- **交付口径**（`count_chars.py`）：只剔首行标题 —— 对着平台字数规格用，越界看它
- **质检口径**（`lint_prose.py`）：剔**所有**标题行 + 独立成行的场景分隔符 —— 作神态/动作密度分母用
- 两者**不必相等**，这不是 bug：`count_chars` 回答"够不够字数"，`lint_prose` 回答"描写薄不薄"。把分隔线与二级标题算进分母只会稀释密度、掩盖"描写太薄"这个本技能最想抓的短板。`lint_prose` 输出里会标注口径，别把两个数字当成对不上。
- 用脚本算，不要目测：`python scripts/count_chars.py <md目录>`

## 批次成品包（每批改完必须产出）

**这是给人读的唯一入口**——不要指望人去 36 个文件里翻出"这一批改了哪几章"。

每批改完，建 `批次成品\<日期>-<批次>（<章号>）\`，里面固定放五样：

| 文件 | 作用 |
|---|---|
| `00-请先读我.md/.docx` | 导读：本批范围、改了什么、**要人回答的几个问题**、怎么读 |
| `<本批章节>.docx` × N | **改后成品**（从交付目录复制过来，直接能读） |
| `<批次>改动说明.docx` | 每章「改前 → 改后 + 原因」表 |
| `自查报告.docx` | 机器自查结果（对照问题本逐条打勾）——**逐章地看** |
| `合卷分析.md/.docx` | **合起来看**：节奏曲线、**人物出场与长期缺席**、开场/结尾重复模式、语言趋势（跑 `analyze_arc.py`） |

> **为什么必须有"合卷分析"**：逐章质检只看得见单章。节奏是否忽紧忽松、某个主要角色是否长期不露面、开场结尾是否一个模子、钩子是否反复同型——**这些只有合起来才看得见**。
> **跑法**：每批（3~10 章）跑一次；卷末跑一次全卷。

人手上有这一个文件夹就够：先读导读（3 分钟），再读成品，最后把意见回过来。

> 交付目录（`007 最终文章\`）是**卷的全量成品**，批次成品包是**这一批的切片**——两者都要有，别互相替代。

## 命名规范（交付文件）

**交付 docx 一律用「中文数字 + 全角冒号」**：`第十七章：上报.docx`。

- 转换前先 `ls` 一眼既有交付目录的命名风格，再决定模板（`md2docx.py` 默认 `第{cn}章：{title}.docx`，可改 `{n}` 用阿拉伯数字）
- 命名不一致会产生**"假重复"文件**：看起来像新版本，其实旧版本还躺在旁边，容易被误判成"已覆盖 / 原文已丢"（真实踩过 G-10）

## 日常体检两个脚本

**文件地图**放 `008 进度\文件地图.md/.docx`：写清「我要干什么 → 去哪」，以及「新产生了什么 → 该放哪」，最后加几条不能破的规矩（原稿只读 / 改前先快照 / 每批必出成品包）。**根目录除 skill 包（.zip）与 `_` 开头的记录文件外，不放散文件。**

**每批完成后查文章位置**：`python scripts/article_index.py <书目录> --write`
——它会告诉你每章在哪一格、当前稿是谁、有没有缺章/断号/空文件/多处当前稿，并生成 `008 进度\文章索引.md`。

**随时体检**：`python scripts/inventory.py <书目录>`
会打印结构树，并检查——根目录有没有散落文件、层是否齐全、交付 docx 命名是否规范、有没有批前快照与批次成品包、原稿有没有被动过（**有正文可对照时才判定，没有正文对照时仅提示 mtime**，不会凭空判"被动过"）。返回码 2 表示有要处理的问题。

**校验词典**（`001 世界观\校验词典.txt`）：格式 `规范写法|错写1|错写2`，供 `check_consistency.py --terms` 使用。**只放真错写，别放合法简称**（口语简称、泛指都正常，放进去就会误报）。

## 脚本退出码（门禁照此写）

| 码 | 含义 | 处理 |
|---|---|---|
| 0 | 正常通过 | 放行 |
| 1 | **有 error，禁止放行**（`lint_prose`）／无法开工（参数错、找不到 edsdk、路径不存在） | 必须改完再走 |
| 2 | 输入里**没有可分析内容**（目录空 / 没有 md / 全是序章 / 全部读不出） | **不是"通过"，是没查成**，先修输入 |
| 3 | 部分完成、有文件被跳过 | 人工判断跳过项 |

> ⚠️ **有"非预期跳过项"时不要当成已通过**——脚本会单独标出「预期内（序章/番外类）」与「非预期，建议改名」，只有后者需要你处理。
> `md2docx.py` 另有自己的码：0 全成功 / 1 无法开工 / 2 有章转换失败 / 3 有跳过项。

## 运行环境与依赖

- **Python 3.9+**，无需 pip 安装任何第三方库（全部标准库）。
- **`md2docx.py` 有硬前置**：需要安装 WorkBuddy 的「本地 Office 编辑」插件（提供 `edsdk.py`）。缺它会在转换时明确报错并提示，不会静默产出空文件。
  找到多个 `edsdk.py` 时**自动择优**（版本新优先、其次修改时间新）并打印选用了哪个；要自己指定用 `--sdk <路径>`，要求必须显式指定加 `--sdk-strict`。
  只认 `workbuddy-local-office-edit` / `workbuddy-office-routing` 两个插件 id 提供的 `edsdk.py` —— 磁盘上其他插件（如 `workbuddy-pptx`）也带同名文件但**不算命中**，不同插件的 SDK 接口不同，混用会调错。
- 输入 md 支持 UTF-8 / UTF-8-BOM / GB18030（GBK 亦可），按序严格回退；三者都解不出时该文件报错并跳过，**不会**静默丢字。
  **"技术上能解但解出来是乱码"也算读不出**（如 Big5/Shift-JIS 被 gb18030 蒙混解成乱码），一律报错跳过，绝不当正常稿统计——否则后续所有校验都拿乱码当"一致"来比，全部误通过。
